# AID Language Specification — v0.1 DRAFT

> Auto-Intelligent Development Language
> Compilation target: WASM (via Rust transpilation)
> Cortex: local-only reasoning engine

## 1. Primitives & Types

```
// Scalars
int, float, bool, string, byte

// Composite
array<T>, map<K, V>, option<T>, result<T, E>

// Special
stream<T>    // async data stream
entity       // structured data (like struct)
```

### Type Inference
Strong, static typing with inference via `:=`

```aid
name := "AID"          // inferred as string
port := 8080            // inferred as int
verbose: bool = false   // explicit
```

## 5. The `reason` Block (Cortex Integration)

The core differentiator. A `reason` block is a **declarative AI function** processed by the local Cortex engine at build time and/or runtime.

### Syntax

```aid
reason <name>(<params>) -> <return_type> {
    goal: "<natural language intent>"
    constraints: [<list of rules>]
    context: [<optional references>]
    examples: [<optional input/output pairs>]
    fallback: <expression>
}
```

### Example

```aid
reason classify_ticket(text: string) -> string {
    goal: "Classify a support ticket into a category"
    constraints: [
        "Return one of: billing, technical, general, urgent",
        "If uncertain, prefer 'general'",
        "Response must be a single word"
    ]
    examples: [
        ("My card was charged twice", "billing"),
        ("Server is down", "urgent"),
        ("How do I reset my password", "technical")
    ]
    fallback: "general"
}
```

### Semantics

- **Build time:** Cortex analyzes the `reason` block, generates an optimized decision tree or embedding lookup, and bakes it into the binary.
- **Runtime:** If the baked logic encounters an input outside its confidence threshold, it falls back to live Cortex inference (still local).
- **`fallback`:** Returned if Cortex confidence is below threshold AND live inference is disabled.
- **Documentation:** Every `reason` block auto-generates a doc entry explaining its decision logic.

### Compile-Time vs Runtime Reasoning

```aid
// Compile-time only (baked into binary, zero runtime cost)
reason(static) optimize_query(sql: string) -> string {
    goal: "Rewrite SQL for index-friendly access patterns"
    constraints: ["Preserve result semantics"]
}

// Runtime only (always calls Cortex)
reason(dynamic) route_request(req: Request) -> Handler {
    goal: "Select the best handler based on request content"
    constraints: ["Latency < 5ms"]
    fallback: default_handler
}

// Hybrid (default) — baked with runtime fallback
reason classify_ticket(text: string) -> string {
    // ...
}
```

## 7. Error Handling

```aid

    // ...
}

// Usage with `try`
fn process() -> result<Data, Error> {
    content := try read_file("config.aid")
    data := try parse(content)
    return Ok(data)
}

// Or explicit match
match read_file("config.aid") {
    Ok(content) => process(content)
    Err(e) => log_error(e)
}
```

## 10. `evolve` Blocks — Self-Improving Code ⭐ (Priority 1)

Code that gets smarter with each deploy. The Cortex tracks how `reason` blocks perform in production and uses that data to optimize them on the next build.

### Syntax

```aid
evolve <reason_block_name> {
    track: true                    // enable input/output logging
    retrain_every: <int>           // re-optimize after N invocations
    min_accuracy: <float>          // alert threshold (0.0 - 1.0)
    storage: "local"               // where to store telemetry (default: local)
    approve: false                 // if true, require human approval before applying new logic
}
```

### Example

```aid
reason classify_ticket(text: string) -> string {
    goal: "Classify support ticket"
    constraints: ["Return: billing, technical, general, urgent"]
    examples: [
        ("My card was charged twice", "billing"),
        ("Server is down", "urgent")
    ]
    fallback: "general"
}

evolve classify_ticket {
    track: true
    retrain_every: 1000
    min_accuracy: 0.95
    approve: true           // human reviews before new logic is baked
}
```

### How It Works

1. **Runtime:** Every call to an evolved `reason` block logs `(input, output, correct?)` locally
2. **Build time:** Cortex reads the telemetry, identifies weak patterns, and generates improved decision logic
3. **Diff report:** The auto-docs show what changed — "Added pattern: tickets mentioning 'invoice' now route to billing (was: general)"
4. **`approve: true`:** Build pauses and shows the proposed changes. Developer accepts or rejects.
5. **Rollback:** Previous logic versions are stored. `aid rollback classify_ticket` restores the last version.

### Evolution History (Auto-Generated)

```
// In build output / docs:
evolve classify_ticket:
  v1 (2026-02-18): 3 patterns, 2 examples → 87% accuracy
  v2 (2026-02-20): 8 patterns, 1247 samples → 94% accuracy  
  v3 (2026-02-25): 12 patterns, 3891 samples → 97% accuracy ✓
```

## 11. `intent` Routing — AI-Native HTTP ⭐ (Priority 2)

Let the Cortex handle request routing by understanding intent, not just URL patterns.

### Syntax

```aid
server.intent(<base_path>) => fn(req) -> Response { ... }
```

### Example

```aid
use std.http

fn main() {
    server := http.new(port: 8080)
    
    // Explicit routes take priority (critical paths)
    server.get("/health") => fn(req) -> Response {
        Response.json({ status: "ok" })
    }
    
    // Intent routing — Cortex analyzes all registered handlers
    // and builds a routing table at compile time
    server.intent("/api") => fn(req) -> Response {
        // Cortex matches based on:
        // - HTTP method
        // - Path segments
        // - Body content / structure
        // - Headers
        // - Registered handler signatures
    }
    
    server.start()
}

// These handlers are auto-discovered by intent routing
fn handle_create_user(user: User) -> result<User, Error> { ... }
fn handle_get_user(id: int) -> option<User> { ... }
fn handle_list_tickets(filter: TicketFilter) -> array<Ticket> { ... }
```

### Semantics

- **Compile time:** Cortex scans all functions in scope, their types, and names → builds an optimized routing table
- **Explicit routes always win** — `intent` only handles unmatched requests
- **Fallback:** Returns 404 with a helpful message if no handler matches
- **Auto-docs:** Generates an API route map showing which handler serves which patterns

## 12. `contract` — Natural Language Validation ⭐ (Priority 3)

Contracts combine interfaces with AI-generated validation. Describe rules in plain language, the Cortex writes the checks.

### Syntax

```aid
contract <Name> {
    "<rule in natural language>"
    "<another rule>"
    
    fn method(params) -> return_type
}
```

### Example

```aid
contract UserAPI {
    "User ID must be positive"
    "Email must contain @ and a valid domain"
    "Role must be one of: admin, editor, viewer"
    "Name must be 2-100 characters, no special symbols"
    
    fn create(user: User) -> result<User, ValidationError>
    fn get(id: int) -> option<User>
    fn update(id: int, changes: UserPatch) -> result<User, Error>
}
```

### How It Works

- **Compile time:** Cortex reads the natural language rules and generates validation functions
- **Runtime:** Every function call through the contract is validated automatically
- **Auto-docs:** Rules appear as human-readable API documentation
- **Type-safe:** Generated validators are fully typed — no runtime string parsing

### Generated Output (visible in docs)

```
// Cortex generates (you never write this):
fn __validate_user(user: User) -> result<(), ValidationError> {
    if user.id <= 0 { return Err(ValidationError("User ID must be positive")) }
    if !is_valid_email(user.email) { return Err(ValidationError("Invalid email")) }
    if !["admin", "editor", "viewer"].contains(user.role) { ... }
    // ...
}
```
